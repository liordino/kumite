# round-2 (run 20260829-134912-d3bb30c)

## product_owner

**Value hypothesis**  
Andante will increase music‑discovery satisfaction for hobbyists by ≥ 20 % (measured via post‑use Likert survey) by allowing them to find tracks at a precise tempo quickly.

**Users & pain**  
1. **Music collectors** (age 18‑45) who sort massive libraries by tempo, spending up‑to 2 hrs filtering playlists.  
2. **Workout trainers** who need “walking‑pace” tracks for slow‑tempo sessions and currently rely on ad‑hoc manual searches, leading to slow prep and missed client expectations.

**Smallest valuable slice**  
A single‑page web app that:  
– pulls the user’s public library from a demo Spotify‑style API,  
– automatically extracts BPM for each track,  
– presents an interactive scatter‑plot of tempo vs. genre,  
– lets the user filter by a target BPM range and instantly load the top 10 matches with preview‑playback.  
This demonstrates end‑to‑end value (tempo filtering → instant playback) without full‑scale data ingestion or licensing contracts.

**Business risks & asks**  

1. Is tempo‑based discovery the real friction point for the identified segments?  
2. What percentage of the target market actively use tempo tags or manual filtering?  
3. Will users be willing to give up privacy to import their libraries for this feature?  
4. How will we monetize: freemium API tier, premium “advanced discovery” pack, or partner with streaming services?  
5. Do we need to secure any licenses (e.g., API usage quotas, third‑party data) before launching the slice?  
6. What early‑adopter incentives will persuade enough users to provide honest satisfaction data?  
7. Are there compliance constraints around user data export/analysis that could delay MVP delivery?

**Feasibility verdict**: **conditional** – buildable if a limited‑scope music‑API (e.g., Spotify Web API) is available and BPM can be derived cheaply.  

**Simplest credible design**  
1. **Frontend** – single‑page React app (or vanilla JS) that authenticates the user via OAuth to the music provider, fetches track metadata (id, name, preview_url).  
2. **BPM service** – tiny Node/Express Lambda that receives a list of track IDs, calls a third‑party BPM detection API (e.g., Echonest‑style) or uses a pre‑computed DB, returns BPM values.  
3. **Data store** – read‑only cache (Redis or in‑memory) for recent BPM results; no persistent DB needed for the MVP.  
4. **Audio playback** – HTML5 `<audio>` element streaming the provider’s 30‑s preview_url.  

*Data flow*: client → OAuth → provider API → BPM service → client renders scatter‑plot → client filters → `<audio>` plays preview.

**Hard parts (ranked)**  
1. **BPM accuracy / rate limits** – mis‑tagged tempos break the core promise; external API quotas can throttle MVP.  
2. **OAuth & user data privacy** – mishandling tokens risks revocation and compliance (GDPR).  
3. **Cross‑origin streaming** – preview URLs may have CORS restrictions; fallback proxies add latency.  
4. **Performance perception** – UI must stay under 200 ms to avoid “slow” connotation of “Andante.”  
5. **Licensing limits** – only preview clips allowed; full‑track playback would need separate agreements.

**Complexity budget** – Cut or defer: persistent user accounts, custom BPM extraction pipelines, advanced visualizations, multi‑region CDN, DRM, and any monetisation plumbing beyond a “free‑trial” flag.  

**Hidden assumptions**  
- Spotify‑type API provides a 30‑s preview for every track.  
- BPM service can return results within 100 ms for ≤ 100 tracks.  
- Users are comfortable granting read‑only access to their libraries.

## reality_check

**Flaw 1: Metrics are self-referential, not behavioral.** The value hypothesis measures "satisfaction via post-use Likert survey"—not task time, not retention. Evidence: product_owner's own text. Failure: users tick a box, no time saved, and the product ships a happy-face meter that says it works while nothing changed.

**Flaw 2: The core feature is outsourced to an API you don't control.** Product_owner promises "instant BPM filtering" as the value; architect admits BPM accuracy and rate limits are Hard Part #1, with a hidden assumption that a service returns results in ≤100 ms for ≤100 tracks. Failure: third-party tempo data mis-tags 5% of a library, user sees wrong BPM, abandons—the discovery promise dies on someone else's database.

**Flaw 3: The target segments are phantoms.** "Workout trainers who need walking-pace tracks" isn't a workout category—trainers program intervals, not steady-state walks. "Music collectors" spending "up to 2 hrs filtering by tempo" is an invented number with no source, and Spotify already ships BPM-sorted running playlists. Evidence: both segment descriptions in product_owner's text. Failure: zero pilot users; no sample exists to measure the 20% claim.

**Strongest objection:** This is a single-filter UI bolted onto an existing API. The pain is fabricated (measured by self-report), the accuracy is outsourced, and the segments don't show up. There's no wedge.

**What would refute me:** A signed pilot with 20 trainers, pre/post task-time deltas (not Likert) showing ≥30% savings, plus independent BPM accuracy ≥95% on a 1,000-track sample. Then I'm wrong.
