# round-1 (run 20260830-221525-0390216)

## product_owner

**Value hypothesis**  
Delivering a single, relevance‑curated daily digest of technical blogs will reduce time spent scrolling and increase completion of reading, thereby increasing perceived usefulness for busy developers.

**Users & pain**  
- *Dev‑stefan* – active software engineer, curator of 3‑5 RSS feeds, overwhelmed by dozens of daily posts; needs a quick overview.  
- *Alex * – student, wants to stay on top of industry news but lacks the focus to sift through feeds.  
Pain: endless unread counters, doom‑scrolling, cognitive overload, and time wasted scanning irrelevant posts.

**Smallest valuable slice**  
- Allow a user to subscribe to any RSS feed.  
- Mark “done” when viewed; no persistent unread counter.  
This MVP requires only feed aggregation and a lightweight batch scheduler, no LLM layer.

**Business risks & asks**  
1. Is there evidence that users will abandon free readers for a paid daily digest?  
2. What pricing model (subscription vs. freemium with premium features) yields sustainable revenue?  
3. How will you address cold‑start relevance without user history—what seed feeds or content signals will you use?  
4. Do you anticipate enough return on investment in AI licensing if the LLM layer is optional?  
5. What retention metrics will confirm that a daily digest reduces scrolling fatigue rather than becoming another notification?

## architect

**Feasibility verdict**: buildable – the core RSS fetch‑/batch pipeline is trivial; the only conditional piece is any LLM ranking layer, which can be omitted for an MVP.

**Simplest credible design**  
1. **Fetcher daemon** (cron or background job) → polls each subscribed feed (HTTP GET, respects `If-Modified-Since`/ETag).  
2. **Store** – lightweight embedded DB (SQLite) persisting items, subscription metadata, and a “date‑bucket” flag.  
3. **Batcher** – runs once per day, selects up‑to‑N newest items per feed, applies a deterministic *relevance predicate* (e.g., filter by length < X, exclude known spam domains, optional keyword whitelist).  
4. **Exporter** – writes the daily batch to a local file (JSON/OPML) and/or serves it via a tiny HTTP UI (static page + JS) where the user can mark items “done”. Done‑state is stored locally.  
5. **Optional LLM wrapper** – a plug‑in that, given the batch JSON, calls a user‑configured LLM endpoint to return a score and a short summary; results are cached alongside items. No write‑back to subscriptions.

All components run on the client machine; no server‑side component is required.

**Hard parts (ranked)**  
1. **Cold‑start relevance** – without interaction data, any automatic ranking is speculative; risk of delivering irrelevant items.  
2. **Feed volatility / rate‑limits** – aggressive polling can hit provider limits or cause throttling; need back‑off logic.  
3. **Deterministic batching across devices** – if a user runs the app on multiple machines, ensuring the same daily batch requires shared state or conflict resolution.  
4. **LLM integration safety** – handling user‑provided API keys, timeouts, and data‑privacy (ensuring raw feed content never leaves the device unless the user opts‑in).  
5. **Local UI consistency** – persisting “done” state offline and reconciling after a day‑change.

**Complexity budget**  
- Drop the LLM ranking for v1; rely on simple rule‑based filters (length, domain whitelist) and let users pin manual “must‑read”.  
- Limit the fetcher to a configurable max‑feeds (e.g., 200) to keep memory/CPU low.  
- Skip cross‑device sync; treat each installation as independent.  
- Use only SQLite + a single‑threaded scheduler; avoid distributed job queues or external cache layers.  

**Hidden assumptions**  
- Users have a reliable, always‑on device to run the daily job.  
- RSS feeds provide proper `Last‑Modified`/`ETag` for efficient polling.  
- The user is comfortable storing API keys locally if LLM is added later.  
- “Done” closure is sufficient feedback; no need for explicit relevance feedback loops.

## reality_check

**Flaw 1: The batch is a fiction.** RSS has no daily cadence. A blog drops 12 posts Monday, zero for a week. Your "small daily batch" either caps and hides content (users miss time-sensitive news) or bursts and recreates the doom-scroll you claim to kill. The idea says "deliver feeds a a small daily batch" — but the feed doesn't care about your calendar. Failure: users unsubscribe from active feeds, or the batch is meaningless noise.

**Flaw 2: Cold start is the product, and you admit you haven't built it.** "What 'curated for relevance' means with no interaction history" is an open question. Without curation, Andante is RSS with a timer — a feature, not a product. The LLM layer is "optional" and requires the user to configure their own provider. Most won't. So v1 ships as a dumb batch reader, users realize it, churn. The differentiation is vaporware until the cold-start problem is solved, and you've stated it isn't.

**Flaw 3: "Paid for with attention" is a contradiction.** Attention is the currency, but the loop is: open app, read, mark done. There is no cost to abandoning. No unread counter, no streak, no social pressure. The "done for today" closure is a gimmick — the user can just close the app forever. Retention requires a reason to return; the idea provides none beyond "content exists."

**Strongest objection:** The cold-start problem *is* the value proposition. You cannot curate without data, you have no data at launch, and you've admitted you don't know what curation means without it. The product is a slower RSS reader with no reason to exist.

**What would refute me:** Evidence that a deterministic heuristic (source reputation, recency, topic clustering) yields enough perceived relevance to retain users with zero personalization — or that users stay for the batch cadence alone, independent of curation quality. Or maybe the user can be the curator, and the doom-scrolling is actually removed by not having anything automatically suggested.
